## 3. GroupBy WITH Salting (Optimized)

Add random salt (0–9) to the key, partial-aggregate on salted keys, then combine per ticker.

**Time:** 0.54s

**Improvement:** -72%

**How it works:**
1. Add salt: NVDA → NVDA_0, NVDA_1, … NVDA_9
2. Phase 1: GroupBy salted_key — ~3,132 NVDA trades split across 10 partitions (~313 each)
3. Phase 2: GroupBy ticker — combine partial counts (tiny dataset)

The bottleneck partition now processes ~313 rows instead of 3,132.

**Note:** On local mode with 40,130 rows, improvement may be small or negative (salting adds an extra shuffle). Benefit is dramatic at cluster scale (millions+ rows, many executors).

## 4. Broadcast Join with Metadata

Enrich trades with sector classification using a small lookup table.

**Metadata table:** 25 rows (ticker, base_price, sector)

**Enriched trades:** 40,130 in 1.55s

**How it works:**
- `broadcast(metadata)` copies the 25-row table to every executor's memory
- Each executor joins its local trade partition against that copy — no network shuffle
- Without broadcast: Spark hash-partitions both sides and shuffles the large table

**When to broadcast:** One side is small enough for executor memory (default threshold ~10MB). Our metadata is 25 rows — perfect candidate.

## 5. Summary

| Technique | Problem | Solution | When to Use |
|-----------|---------|----------|-------------|
| Salting | Hot keys → straggler partitions | Split key into N sub-keys, partial agg, combine | GroupBy/join on skewed keys (>10x volume difference) |
| Broadcast join | Shuffling small table wastes network | Send small table to all executors | One table < 10MB (dimension tables, lookups) |
| Partition tuning | Too many/few partitions | Match to executor cores | `spark.sql.shuffle.partitions` (default 200; we use 4 locally) |

## 6. TCS Context

At TCS, I applied these same techniques on revenue reconciliation pipelines processing 250GB+ monthly:
- **Salting:** Customer ID skew — top 5 enterprise customers had 60% of transactions. Salting reduced stage runtime from 45 minutes to 18 minutes.
- **Broadcast join:** Product catalog (50K rows) joined with 200M transactions. Broadcast eliminated a 15-minute shuffle stage.
- **Partition tuning:** Reduced shuffle partitions from 200 to 48 (matching our 48-core cluster), cutting overhead from partition management.
